# Harness 重要吗？开发者该把精力花在哪里

最近 Astra 出来以后，我感觉自己又回到了一个很熟悉的状态：想做的事情太多，额度太少。按我自己的用法，GPT Plus 一天的额度，二十分钟就能烧光。

没有 Token 的日子，真的少了很多乐趣。脑子里冒出一个想法，却不能马上动手让它跑起来。最后实在忍不住，开了二十倍。用了以后，只能说，确实爽。

但这几天真正让我有感触的，并不是额度终于够了，而是折腾 DeepSeek Harness 插件开发的这段经历。

最开始，我用过一些小模型，也试过让 DeepSeek 开发自己的插件。过程中撞了不少墙。同一个问题，读代码、改代码、再测试，来来回回，却没有真正解决。后来换 GPT 把事情收了尾，我对模型能力差距的感受一下子变得特别具体。

这当然只是我的实际开发经历，不是严格的模型评测。但它让我意识到：模型能力会影响一个 Agent 到底能不能把工程任务做完。与此同时，模型外面的运行系统，也会影响它能不能稳定地做完。

以前做一些 AI 应用，我习惯先接一个聊天窗口。但到了工业企业的使用场景，光能聊天是不够的。

用户真正关心的是：这件事做对了吗？成功率有多少？每一步发生了什么？失败能不能恢复？什么时候要人来接管？输出有没有证据？成本和等待时间能不能控制？

所以产品里需要的，往往是一个 Agent 的任务运行界面。它可以是图形化的：任务走到了哪里，执行了什么工具，检查了哪些证据，哪里卡住，下一步该谁处理。形式上可以像流程画布，但背后必须有真实、可追踪的执行状态。

我也尝试过自己写一套编排程序。写出来不等于稳定运行。后来我开始想，这些通用运行能力，是否应该优先复用成熟的开源系统？比如 Codex 这样的底座，能不能承接业务 workflow？

于是我拿一个法律 Agent 项目做了对照测试。

这次查代码，先发现了一个很实际的问题：项目里虽然有一组叫 CodexLaw，但旧入口只是调用模型，再接自建的状态和引用校验，没有真正运行 Codex。名字不能替代实现。

后来我们把原生 Codex CLI 真正接通了。模型还是 MiniMax-M3，通过兼容转接层接入。第三方模型和原生 Codex 编排并不冲突，关键是实际走哪条调用链。

接通以后，还要继续检查实验条件。两边是不是同一份证据？输出预算和超时是否一致？有没有偷偷加载个人指令和插件？失败究竟是答案不对、格式问题、引用问题，还是 Token 用完了？这些都需要真实记录。

我们也发现向量服务虽然能调用，索引格式却缺了模型要求的前缀。于是保留旧索引，重新构建了五万八千多条向量，再把图数据库部署到 DGX，让图谱查询真正进入准备流程。两边最后拿到同一份冻结的检索结果。

这次完整跑完六十道题，Lawgent 通过三十七道，原生 Codex 路径通过四十八道。通过率从百分之六十一点六七到百分之八十，增加十八点三三个百分点。但拆开看，有三道失败仅仅是对象转文本时弄坏了格式；还有三次中间网络调用失败，流程后来恢复了。数字要讲，数字背后发生了什么，也要讲清楚。

旧数据也保留。在过去一批六十道题里，两边差十个百分点；但另一批反而下降六点六七个百分点。这些批次条件不同，而且旧版没有真正调用 Codex，所以不能拿它们拼成一个漂亮的“原生 Harness 提升”结论。

现在我们能更明确地说每一条记录发生了什么。比如有的模型调用正常结束，答案也藏在返回对象里，却在工作流转成文本的时候丢掉了 JSON 格式。这样的失败和法律判断错误，需要分开理解。

所以我现在更想问的是：Harness 重要吗？它是不是开发者值得长期投入的事情？

我的看法是，它重要，但不同角色应该投入的地方不一样。

对模型厂商和基础设施提供者来说，Harness 很重要。它承接模型、工具、任务状态、权限、恢复和交付。开发者依赖了这个底座，很多应用能力就会在上面长出来。某种程度上，它有一点像操作系统。

对业务开发者来说，我越来越不想重新造一遍这些通用机制。如果成熟系统已经能把任务运行、状态保存、工具调用和错误恢复做好，我更愿意复用它，把精力放在业务本身。

但复用底座，不意味着把业务正确性也外包掉。企业里的验收标准、证据要求、审批权限、失败补偿、人工接管，仍然要由懂业务的人定义。尤其是法律这样的场景，“任务运行结束”和“结果可以信任”，是两件必须分别验证的事。

所以我的做法是，先接通真实运行底座，再把共同条件和失败记录做扎实。这个实验只覆盖同证据、禁外部工具的任务，不代表完整自主 Agent 的全部能力。接下来继续让数据告诉我：哪些东西值得自己做，哪些东西直接复用就够了。

对于开发者，长期值得积累的，可能是如何把业务变成能执行、能检查、能交付的系统。通用 Harness 可以换，业务里的判断标准和验证能力，会留下来。
